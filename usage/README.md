# Usage metrics (agent token spend)

Data captured from the local Hermes runtime and committed to this `usage`
branch so the CI/DAG pipeline can audit agent spend against the lineage.

## Two data sources

The audit spans **both** scheduled and interactive work:

| Source | What it captures | File |
|---|---|---|
| `cron/usage_audit.jsonl` | Scheduled/cron job runs (timestamp, prompt/completion tokens, model, duration, error) | `raw/usage_audit.jsonl` |
| `state.db` → `session_model_usage` | Interactive/agent session turns — per-session per-model API calls, input/output/cache/reasoning tokens, cost fields | `raw/state_session_usage.tsv` |

Neither alone is a full picture; together they cover the two ways the agent
spends tokens.

## Message time-budget ledger

The primary bottleneck is **user messages**, not inference compute. Every
human user message in the target chat is tracked and billed so message-time
can be managed and rationalised against token-spend investment.

Billing model (as specified):
- USD 20.00 flat per user message.
- A message with N paragraphs (blank-line separated) counts as N messages,
  so a 3-paragraph message bills $60.
- Size is measured as a real BPE token count (`tiktoken` cl100k_base, with a
  stdlib byte-pair fallback if tiktoken is absent).

Generated by `user_messages.py`:
- `user_messages_ledger.tsv` — per-message metadata: message id, principal
  (mark/derek/other), sender id, timestamp, utf-8 bytes, BPE tokens,
  paragraph count, billed USD, truncated content hash.
- `user_messages_by_principal.tsv` — totals grouped by principal.
- `user_messages_content.tsv` — message bodies, Fernet-encrypted by default
  (ciphertext is committable; plaintext only via key + `--plaintext`).

PRIVACY & DISCLOSURE: user-messages are treated as source code — committing
raw prose is acceptable, but by default the ledger encrypts message bodies
(Fernet/AES) into `user_messages_content.tsv`.  The ciphertext is safe to
commit/push; plaintext is only obtainable with the key.  Keys are kept
OUTSIDE the repo (env `R2DP_LEDGER_KEY` or `R2DP_LEDGER_KEYFILE`); generate
one with `user_messages.py make-key`.  To emit plaintext for a specific
approved message, run with the key and `--plaintext` locally and disclose
selectively — do not commit the plaintext file.

## Contents

- `raw/usage_audit.jsonl` — verbatim copy of the runtime cron audit log
  (timestamp, job_id, fire_id, prompt/completion/total tokens, model,
  duration_ms, error). One JSON object per line.
- `raw/state_session_usage.tsv` — extract of `session_model_usage` from the
  runtime `state.db` (one row per session×model accounting line).
- `aggregate_by_model.tsv` — runs / total_tokens / duration_s grouped by model.
- `aggregate_by_day.tsv` — runs / total_tokens grouped by day.
- `aggregate_by_model_sessions.tsv`, `aggregate_by_day_sessions.tsv` —
  session-source aggregates (calls / input / output / cache / reasoning).
- `normalize.py` — reads `raw/usage_audit.jsonl`, emits the cron TSVs; the
  canonical regeneration path for the cron source.
- `extract_state_usage.py` — reads live `state.db` and writes the session
  raw TSV + session aggregates (idempotent; `-` skips the live read).

## Planned audit coupling to the lineage DAG

Cross-reference agent token spend against the lineage-DAG CI:

- Each DAG commit already builds/tests in isolation (`tests/ci_dag.sh`,
  lineage branch). Attach a usage-audit step that records tokens consumed
  per commit run, keyed by commit SHA, into a per-branch metric.
- `normalize.py` + `extract_state_usage.py` output is the lineage of the
  spend: model × job/session × day, so a regression (a commit or session
  that balloons prompt tokens) is visible in the same DAG walk.
- The audit aspect is intentionally minimal here (baseline); it will be
  extended in the lineage-DAG CI as the cross-reference matures.
